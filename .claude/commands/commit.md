git add がされている変更をコミットし、必要であればドキュメントを更新する。

## 手順

### 1. 変更内容の把握
`git diff --staged --name-only` で変更ファイルを確認する。
変更がなければ「ステージングされた変更がありません」と伝えて終了する。

### 2. ドキュメント更新の要否判定

**更新不要（そのままコミットする）**
- リファクタリングのみ（処理内容が変わっていない）
- コメント・typo の修正
- テストの追加のみ（ビジネスルールの変更なし）
- スタイル・CSS の変更のみ

**更新が必要**
- ビジネスルール・処理条件の追加・変更
- 新機能の追加
- 状態遷移・権限の変更
- 他ドメインへの副作用が生じる変更

### 3. ドキュメントの更新

更新が必要と判断した場合、以下を行う。

**既存ドメイン・機能の変更の場合**
- docs/domain/ または docs/features/ の該当ファイルを更新する
- 更新内容：ビジネスルールと調査起点のみ。実装の詳細は書かない
- 仕様書と実装に矛盾がある場合：更新前に報告して確認を求める

**新規ドメインの場合**
- docs/domain/_template.md をコピーして新規ファイルを作成する
- docs/index.md のドメイン一覧に追記する

**新規機能の場合**
- docs/features/_template.md をコピーして新規ファイルを作成する
- 関連するドメインファイルの「関連機能」に wikilink を追記する
- docs/index.md の機能一覧に追記する

**ADR が必要な場合**（なぜそう実装したか説明が必要な設計判断）
- docs/adr/_template.md をコピーして連番で作成する
- 関連する機能ファイルの「ADR」セクションにリンクを追記する

### 4. コミットの実行

ドキュメントを更新した場合は、変更ファイルと一緒にステージングしてコミットする。

```
git add docs/
git commit -m "..."
```

コミットメッセージは Conventional Commits 形式で書く：
- feat: 新機能
- fix: バグ修正
- docs: ドキュメントのみの変更
- refactor: リファクタリング
- test: テストの追加・修正

### 5. 完了報告

以下を簡潔に伝える：
- コミットしたファイル
- ドキュメントを更新した場合はどのファイルを何の理由で更新したか
- ドキュメントを更新しなかった場合はその理由
